# Handoff: planejamento inicial (2026-10-02)

Resumo de uma conversa de planejamento feita fora do repositório, no Claude.ai. Serve para a primeira sessão no Claude Code começar com todo o contexto. Para o que o projeto é, leia `brief.md`; aqui ficam as decisões, quem as tomou, o que está em aberto e por onde começar.

## Como ler este documento

- **Decidido pelo Heron:** vale como requisito.
- **Proposto pelo Claude:** foi recomendado e aceito em linhas gerais, mas os detalhes ainda podem mudar. Os ADRs correspondentes estão com status **Proposta**.
- **Em aberto:** precisa de decisão antes do marco indicado. Não decida sozinho: apresente as opções e pergunte.

## Decisões do Heron

1. O projeto existe para demonstrar domínio técnico, principalmente na AWS: **load balancer com autoscaling e encolhimento em horários de pouco uso**. O objetivo não é economizar; o custo é controlado destruindo a stack fora dos períodos de demonstração.
2. **Backend na AWS** (ECS, ALB e serviços gerenciados), não em homelab nem em VPS.
3. **Git Flow com PRs como evidência** do desenvolvimento e da cadência de trabalho. Todo o projeto segue esse fluxo, desde o setup.
4. **Primeiro PR é o setup:** estrutura de pastas, `CLAUDE.md` e documentação.
5. **CI/CD completo:** frontend com deploy seguro na Cloudflare via wrangler; backend publicando imagem pública quando uma tag é criada.
6. **Registry na AWS (ECR)** em vez do Docker Hub, com imagem pública.
7. Estrutura de pastas na raiz: `backend`, `frontend`, `terraform` e `.ia_context`, acrescida de `docs/`, `loadtest/` e `.github/`.
8. Descrição e topics do repositório no GitHub já definidos (descrição em inglês, mencionando "play money only").

## Propostas aceitas em linhas gerais

- Monorepo NestJS com três serviços (`gateway`, `round-engine`, `settlement-worker`) e `libs/domain` em TypeScript puro.
- Domínio com `Round`, `Bet` e `Wallet`; saldo por ledger imutável; idempotência na aposta; lock otimista no saque.
- Provably fair por commit e reveal com HMAC-SHA256.
- SNS → SQS com DLQ para liquidação.
- ECS Fargate, RDS, ElastiCache; EKS descartado por custo de control plane.
- Autoscaling por métrica customizada de conexões WebSocket ativas, ações agendadas e drenagem no scale-in.
- ECR privado (deploy) e ECR Public (vitrine), push via OIDC, cosign, tags imutáveis.
- Merge commit em PRs de feature para preservar os commits de TDD.
- Página do Crash Arena no portfólio consulta `/health` e cai para simulação no navegador quando a API não responde.
- Marcos m0 a m8, conforme o roadmap do README.

## Por onde começar

### PR 1 (m0): setup

O GitHub exige um primeiro commit, então:

1. Commit inicial em `main` com README mínimo e licença MIT.
2. Criar `develop` a partir de `main` e defini-la como branch padrão.
3. Branch `feature/m0-project-setup` com tudo o que está nesta entrega: `CLAUDE.md`, `README.md`, `docs/` (arquitetura, Git Flow, CI/CD, ADRs 0001 a 0012), `.ia_context/`, `.github/pull_request_template.md` e `.github/dependabot.yml`. Acrescentar `.gitignore` (Node, Terraform, `.env`), `.editorconfig` e um `README.md` curto em `backend/`, `frontend/`, `terraform/` e `loadtest/` dizendo o que cada pasta vai conter e em qual marco.
4. Abrir o PR para `develop`, com o template preenchido.
5. Configurar no GitHub: proteção de `main` e `develop` (só PR, CI obrigatório quando existir, sem exigir aprovação), milestones m0 a m8, Project com quatro colunas, secret scanning e push protection.
6. Depois do merge: `release/v0.0.1` → `main`, tag `v0.0.1` e GitHub Release.

### PR 2 em diante (m1): domínio

Antes de codar, criar `.ia_context/plans/round-m1-domain.plan.md` com: a fórmula do crash, a máquina de estados da rodada, os testes a escrever primeiro e o que fica fora. Resolver antes as pendências de idioma e test runner. O PR 2 também traz `package.json`, `tsconfig`, o runner de testes e o primeiro workflow de CI. Sugestão de fatias para o m1: agregado `Round`; value object do provably fair; agregado `Bet`; `Wallet` com ledger.

## Como trabalhar com o Heron

- Planejar primeiro e esperar confirmação antes de aplicar. Em infraestrutura, diagnosticar antes de propor comandos; nada de tentativa e erro.
- Separar o que a documentação afirma do que foi confirmado no caso concreto. Não declarar "bug" sem evidência.
- Diffs pequenos e direcionados, não reescritas completas.
- Tom direto e analítico, em português.
- O repositório é público: nada de nomes de empregadores, clientes, dados internos ou menções a processos seletivos nos arquivos versionados.
